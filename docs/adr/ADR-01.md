# ADR-01: Выбор режима инференса

## Статус

Принято.

## Контекст

Проектируемая система — внутренний AI-ассистент для команды Data Science. Основные сценарии — интерактивные вопросы пользователей через UI (Gradio) и REST API. Требования SLA: `/chat` p95 < 7 сек, `/agent` p95 < 20 сек, TTFT < 1 сек. Нагрузка — десятки запросов в час от небольшой команды.

Необходимо выбрать режим инференса: синхронный REST API или асинхронная очередь сообщений.

## Альтернативы

1. **Синхронный REST API** — клиент отправляет запрос и ждёт ответа в рамках одного HTTP-соединения.
2. **Асинхронная очередь сообщений** (Kafka / RabbitMQ / Redis Streams) — запрос публикуется в очередь, результат забирается отдельно (polling / webhook / WebSocket).

## Решение

Выбран **синхронный REST API** (FastAPI).

## Обоснование

- SLA (p95 < 7 сек для `/chat`, < 20 сек для `/agent`) укладывается в таймауты HTTP-клиентов.
- Интерактивный характер взаимодействия: пользователь ожидает ответ в реальном времени.
- Отсутствие требований к гарантированной доставке, повторной обработке и горизонтальному масштабированию на тысячи RPS.
- Простота реализации, отладки и эксплуатации: не нужны брокер, воркеры, отдельный мониторинг очереди.
- Асинхронная очередь добавила бы инфраструктурную сложность без выгоды для текущего профиля нагрузки.

## Последствия

**Положительные:**

- Простая архитектура, минимум инфраструктуры.
- Лёгкая отладка и локальный запуск.
- Прямая интеграция с Gradio UI.

**Отрицательные:**

- Нет встроенной устойчивости к пиковым нагрузкам (backpressure).
- Долгие запросы занимают HTTP-соединение.
- При росте нагрузки потребуется пересмотр решения (переход к очереди или стримингу).

**Митигации:**

- Стриминг ответа (SSE) для снижения TTFT.
- Горизонтальное масштабирование контейнера `app` за reverse-proxy.
