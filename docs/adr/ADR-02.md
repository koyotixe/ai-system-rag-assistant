# ADR-02: Стратегия хранения и версионирования моделей

## Статус

Принято.

## Контекст

Система использует:

- эмбеддер `intfloat/multilingual-e5-small` (384-dim);
- LLM через OpenRouter (внешний API, веса не хранятся локально);
- корпус документации scikit-learn (~267 чанков) в виде JSONL.

Необходимо определить, как хранить и версионировать артефакты моделей и данные, чтобы:

- не раздувать Git-репозиторий;
- обеспечить воспроизводимость;
- подготовить путь к production-эксплуатации.

## Альтернативы

1. **Хранение бинарных весов в Git** (Git LFS или напрямую).
2. **HuggingFace Cache + JSONL для чанков** (локально), с переходом на **DVC + S3** или **MLflow** в production.
3. **Полный отказ от локальных артефактов** — загрузка модели при каждом старте контейнера.

## Решение

- **Запрет на бинарные веса в Git** (`.gitignore`: `*.pkl`, `*.pt`, `*.onnx`, `*.bin`, `*.safetensors`).
- **Локально:** HuggingFace Cache для весов эмбеддера + `data/corpus_chunks.jsonl` (исключён из Git).
- **В production:** DVC + S3 (или MLflow Model Registry) для версионирования артефактов.

## Обоснование

- Git плохо подходит для бинарных файлов: раздувание истории, медленные клоны.
- HuggingFace Cache — стандартный механизм для `sentence-transformers`, автоматически управляет версиями.
- JSONL — простой, читаемый, потоковый формат для чанков; легко диффить и версионировать.
- DVC + S3 / MLflow — индустриальный стандарт для версионирования ML-артефактов в production.
- Разделение «локально просто / production строго» позволяет быстро стартовать и масштабироваться.

## Последствия

**Положительные:**

- Чистая история Git, быстрые клоны.
- Воспроизводимость через фиксацию версий моделей и хешей датасетов.
- Готовность к production-пайплайну.

**Отрицательные:**

- Требуется настройка DVC / MLflow при переходе в production.
- Нужно документировать версии моделей и датасетов отдельно от кода.

**Митигации:**

- Фиксация версий в `requirements.txt` и конфигурации.
- Хеширование `corpus_chunks.jsonl` и сохранение хеша в метаданных.
