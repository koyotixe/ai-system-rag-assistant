3. Теоретические сведения
3.1. Архитектура программной системы искусственного интеллекта
    Архитектура программной AI-системы — это совокупность фундаментальных решений об организации программного продукта: декомпозиция на независимые или слабосвязанные модули, выбор способов обмена информацией, организация контуров хранения, размещения и эксплуатации.
    В отличие от традиционных информационных систем, архитектура AI-системы обязана изолировать и гармонизировать четыре параллельных контура:
    1. Контур данных (Data Pipeline / DataOps): источники, очистка, версионирование сырых данных и витрин признаков (DVC / S3), валидация схем.
    2. Контур модели (Model Lifecycle / MLOps): обучение, валидация, реестр моделей (MLflow / Model Registry), хранилище весов.
    3. Прикладной контур (Application & Serving): API Gateway, бизнес-логика, пользовательский интерфейс, авторизация.
    4. Эксплуатационный контур (DevOps & Observability): контейнеризация (Docker), CI/CD (GitHub Actions), логирование (JSON), сбор технических метрик (Prometheus) и метрик качества данных (Evidently).
3.2. Архитектурные стили в AI-приложениях
    * Модульный монолит (Modular Monolith): приложение собирается и развертывается как единый исполняемый артефакт (единый Docker-контейнер), однако внутри код строго разделен на независимые модули с явными контрактами (api/, services/, ml/, data/, storage/). Рекомендуется как базовый стартовый стиль для учебных и большинства прикладных проектов.
    * Микросервисная архитектура (Microservices): разделение приложения на независимые сетевые сервисы (отдельно API Gateway, отдельно сервис инференса модели, отдельно сервис очередей). Оправдана при наличии тяжелых моделей, требующих GPU, разных жизненных циклов релизов или независимого масштабирования.
    * Событийно-ориентированная архитектура (Event-Driven): асинхронное взаимодействие через брокеры сообщений (Kafka, RabbitMQ, Redis Streams). Применяется при высоких нагрузках, пакетной обработке очередей файлов или обработке потоковых данных с датчиков (IoT).
3.3. Опасность Train-Serving Skew
    Одна из ключевых архитектурных ошибок ML-систем — расхождение логики предобработки данных при обучении и в рабочем сервисе. Архитектура должна гарантировать, что модули трансформации признаков (Feature Transformers) сохраняются как версионированные артефакты и импортируются сервисом инференса в неизменном виде.

5.1. Главный эндпоинт инференса: POST /api/v1/predict
* Заголовки: 
Content-Type: application/json, X-API-Key: <secret_token>.
* Схема входных данных (JSON Schema / Pydantic):
from pydantic import BaseModel, Field
from typing import Optional
from uuid import UUID

class PredictionRequest(BaseModel):
    item_id: str = Field(description="Уникальный идентификатор объекта / транзакции / пользователя")
    # Доменные признаки (пример для задачи предиктивного обслуживания):
    temperature: float = Field(ge=-50.0, le=250.0, description="Температура узла, °C")
    vibration_amplitude: float = Field(ge=0.0, le=100.0, description="Амплитуда вибрации, мм/с")
    operating_hours: int = Field(ge=0, description="Наработка в часах")
    error_code_last_24h: int = Field(ge=0, le=999, default=0, description="Код последней ошибки")

    class Config:
        json_schema_extra = {
            "example": {
                "item_id": "PUMP_UNIT_42",
                "temperature": 82.5,
                "vibration_amplitude": 4.12,
                "operating_hours": 1420,
                "error_code_last_24h": 12
            }
        }

* Схема успешного ответа (200 OK):
class PredictionResponse(BaseModel):
    request_id: str = Field(description="Уникальный идентификатор запроса (UUIDv4) для аудита")
    item_id: str = Field(description="Идентификатор переданного объекта")
    prediction: str = Field(description="Текстовый вердикт (например: 'CRITICAL_RISK', 'NORMAL')")
    probability: float = Field(ge=0.0, le=1.0, description="Вероятность наступления целевого события")
    model_version: str = Field(description="Семантическая версия используемой модели")
    manual_review_required: bool = Field(description="Флаг необходимости проверки оператором")

* Пример тела успешного ответа:
{
  "request_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",

Этап 6. Архитектурные решения (Architecture Decision Records — ADR)
    В каталоге docs/adr/ (или прямо в теле итогового отчета) оформите три обязательных документа ADR по промышленному формату:
Шаблон ADR:
### ADR-01: [Название решения]
- **Статус:** Принято (Accepted)
- **Контекст:** [Какая инженерная проблема возникла, какие ограничения учитывались]
- **Рассмотренные альтернативы:** 
  1. [Вариант А]
  2. [Вариант Б]
- **Решение:** [Что именно выбрано]
- **Обоснование:** [Почему этот вариант оптимален с точки зрения баланса компромиссов (Trade-offs)]
- **Последствия:** [Преимущества решения и связанные с ним технические риски/ограничения]

Обязательные темы для трех ADR:
    1. ADR-01: Выбор режима инференса (Synchronous REST API vs Asynchronous Message Queue).
    Выбор: для большинства учебных проектов принимается синхронный REST API (FastAPI) с обоснованием простоты реализации, низких задержек при одиночных запросах и достаточной пропускной способности.
    2. ADR-02: Стратегия хранения и версионирования моделей и артефактов.
    Выбор: запрет на хранение бинарных весов модели в Git. Хранение метаданных и DVC-файлов в Git, а реальных артефактов — в S3-хранилище (MinIO) или версионированном реестре моделей MLflow.
    3. ADR-03: Архитектурный стиль сервиса (Модульный монолит vs Микросервисы).
    Выбор: модульный монолит в едином контейнере Docker. Обоснование: отсутствие избыточных сетевых задержек, простота локальной отладки и тестирования, низкая нагрузка на первом этапе проекта.

Этап 7. Проектирование безопасности, наблюдаемости и устойчивости
7.1. Информационная безопасность и защита данных
* Опишите механизм аутентификации внешних вызовов (передача ключа в заголовке X-API-Key).
* Защита от DoS/DDoS: ограничение размера полезной нагрузки (Payload Size Limit до 2 Мб), валидация тайм-аутов запроса.
* Соблюдение 152-ФЗ и приватность: исключение передачи персональных данных (ФИО, телефоны, паспортные данные) в незашифрованном виде; маскирование идентификаторов перед подачей на инференс.
7.2. Наблюдаемость (Observability) и аудит
* Формат логов: структурированное JSON-логирование каждого входящего запроса:
{"timestamp": "2026-09-14T12:00:00Z", "level": "INFO", "request_id": "...", "item_id": "...", "latency_ms": 12.4, "status": 200, "prediction": "NORMAL", "model_version": "1.0.0"}

* Метрики сервиса (Prometheus):
o http_requests_total (счетчик запросов по кодам ответа);
o http_request_duration_seconds (гистограмма задержек);
o model_inference_duration_seconds (чистое время инференса).
* Контроль дрейфа данных (Data & Concept Drift): сбор логов входящих векторов признаков для периодического offline-анализа статистического расхождения распределений (тесты Колмогорова-Смирнова, Population Stability Index — PSI через библиотеку Evidently).

# Система предиктивного обслуживания оборудования: Architecture Blueprint

## 1. Контекст системы
Сервис предназначен для непрерывного анализа телеметрических показателей станков ЧПУ (вибрация, температура подшипников, ток двигателя) с целью выявления аномалий и предупреждения аварийных остановок.

## 2. Архитектурный стиль
Выбран архитектурный стиль **клиент-серверного модульного монолита** с упаковкой в единый Docker-контейнер на базе FastAPI. Причина: высокая скорость инференса на CPU (до 20 мс), небольшая команда (1 разработчик), отсутствие необходимости в GPU-кластере на первом этапе эксплуатации.
